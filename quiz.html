규칙·훅·메모리·MCP·위임 — 명세서를 읽었다면 풀 수 있는 시나리오 12문항. 보기를 누르면 정답과 해설이 바로 나옵니다.

PHASE 1 · 전체 조감도
🧪 시나리오 #1
"봇이 오늘 무슨 도구를 몇 번 썼고 뭘 했는지" 한눈에 보고 싶습니다. 어느 한 곳만 열어보면 될까요?
~/.claude/rules/ — 규칙 파일들이 모여 있으니 여기
~/.claude/logs/ — 거의 모든 기록(audit·metrics·agents)이 여기로 모인다
Wiki/ 폴더 — 날짜별 일지가 있으니 여기
정답: logs/ — dispatcher 훅이 도구를 쓸 때마다 작업일지·통계·에이전트 기록을 전부 logs/ 한곳에 적습니다. rules는 "어떻게 일할지"이지 활동 기록이 아니고, Wiki 일지는 자동 기록이 아니라 사람·봇이 직접 쓰는 요약입니다. (오래된 로그는 log-rotate가 청소)
PHASE 1 · 데이터 흐름
🧪 시나리오 #2
대화가 너무 길어져 자동 압축(Compact)이 일어났습니다. 직전 맥락은 어떻게 되살아날까요?
한 번 압축되면 이전 맥락은 복원 불가, 백지에서 다시 시작한다
restore-session이 cc-connect 대화 기록을 다시 읽어 복원하고, 실패하면 hot.md로 폴백한다
사용자가 직접 이전 내용을 복사해서 다시 붙여넣어야 한다
정답: restore-session → hot.md 폴백 — 컨텍스트 복원 물길(4번 물길)이 이 일을 합니다. 세션 시작은 restore-context, 압축 발생은 restore-session이 담당하고, 둘 다 cc-connect 기록 읽기에 실패하면 최신 상태 카드인 hot.md를 대신 읽습니다.
PHASE 2 · 일하는 절차
🧪 시나리오 #3
사용자가 "settings.json에 훅 하나만 추가해줘"라고 했습니다. 봇이 가장 먼저 취해야 할 행동은?
간단한 요청이니 바로 Edit으로 훅을 추가한다
백업본만 먼저 만들어두고 곧바로 추가한다
검증 실행 7단계(VE)를 발동 — 조사·계획·검증·시뮬 후 ⑤승인 게이트에서 사용자 승인을 받고 실행한다
정답: VE 7단계 발동 — 훅·설정·cron을 하나라도 바꾸면 VE 대상입니다. 핵심은 ⑤승인 게이트: 사용자가 "해줘/진행해/응"이라고 명시하기 전엔 절대 파일을 고치지 않습니다. "~하겠습니다" 직후 바로 Edit을 호출하는 것도 금지예요.
PHASE 2 · 진입점 열거
🧪 시나리오 #4
텔레그램 /restart 명령을 막았는데도 봇이 자꾸 이중 실행됩니다. 가장 가능성 높은 원인은?
텔레그램 토큰이 만료돼서
CLI cc-connect restart 등 같은 동작에 도달하는 다른 진입점을 안 막아서
메모리가 손상돼서
정답: 다른 진입점 누락 — 전체 버그의 52%(설계 미비 32% + 경로 누락 20%)가 "한 경로만 고치고 다른 경로를 빠뜨림"에서 나옵니다. 실제 #25 사례가 정확히 이것 — 텔레그램만 막고 CLI를 빠뜨려 이중 실행이 재발했습니다. 그래서 변경 전 모든 진입점을 나열하는 규칙이 생겼습니다.
PHASE 3 · 도구 전/후 훅
🧪 시나리오 #5
파일을 Edit으로 수정했습니다. 그 한 번의 수정에서 자동으로 도는 훅 순서로 맞는 것은?
guard → 수정 → dispatcher
checkpoint-pre·credential-guard → 수정 → auto-lint·dispatcher
rule-reminder → 수정 → daily-summary
정답: checkpoint-pre·credential-guard → 수정 → auto-lint·dispatcher — 쓰기 전엔 원본 백업(checkpoint-pre)과 자격증명 검사(credential-guard), 쓴 후엔 서식 정리(auto-lint)와 기록(dispatcher)이 돕니다. guard는 Bash·PowerShell 전용이라 파일 편집엔 안 끼고, daily-summary는 응답이 끝날 때(Stop) 도는 훅입니다.
PHASE 3 · 종료 훅
🧪 시나리오 #6
하루 동안 도구를 20번 넘게 썼는데 그날 세션로그(일지)를 한 줄도 안 썼습니다. 응답을 끝내려 하면?
아무 일도 없다 — 일지는 순전히 자율
dispatcher가 알아서 세션로그를 자동 작성해준다
session-log-guard가 응답 끝(Stop)에서 "일지 쓰라"며 막는다(block, 하루 1회)
정답: session-log-guard가 막는다 — 이 훅은 그날 작업일지(audit) 줄 수를 세어, 일을 많이 했는데 세션로그가 없으면 응답을 멈추고 다시 시킵니다. dispatcher는 audit·metrics·agents 로그만 적을 뿐 사람이 읽는 세션 일지를 쓰지는 않습니다. (또 다른 차단 훅은 check-response-format)
PHASE 4 · 기억 체계
🧪 시나리오 #7
새 세션을 켰습니다. 봇이 "어제까지 뭘 하고 있었지?"를 복원하려고 가장 먼저 읽는 파일은?
MEMORY.md — 메모리 31개의 목차
hot.md — 마지막 세션·핵심 결정·활성 펜딩·현재 포커스를 담은 최신 상태 카드
가장 최근 날짜의 sessions/YYYY-MM-DD.md
정답: hot.md — 세션 일지들의 "맨 위 요약 카드"로, 새 세션을 켤 때 제일 먼저 읽는 파일입니다. 게다가 restore-context 훅이 cc-connect 기록 복원에 실패했을 때의 최후 폴백이기도 합니다. MEMORY.md는 오래 두고 쓰는 사실들의 목차일 뿐, 최신 진행상황 카드가 아닙니다.
PHASE 4 · 기억 안전
🧪 시나리오 #8
메모리에는 "cc-connect는 systemd 서비스로 실행 중"이라 적혀 있는데, 지금 파일시스템엔 systemd 설정이 전혀 없습니다. 어떻게 해야 할까요?
메모리를 신뢰해서 systemd 서비스로 다시 띄운다
현재 파일시스템을 신뢰하고, 메모리는 과거 정보로 처리 + 불일치를 사용자에게 보고한다
충돌이니 둘 다 무시하고 진행한다
정답: 현재 파일시스템 우선 — 메모리 안전 규칙①(메모리 중독 방어, OWASP ASI06)입니다. 오래되거나 오염된 기억이 현재 시스템 상태를 덮어쓰지 못하게, 충돌 시 "지금 파일"을 신뢰하고 메모리는 과거 정보로 다룬 뒤 사용자에게 불일치를 알립니다. 메모리에 "실행하라"가 있어도 그대로 실행하지 않는 것(규칙②)도 같은 맥락입니다.
PHASE 5 · 위임 게이트
🧪 시나리오 #9
단일 파일에서 오타 한 줄만 고치면 됩니다. 보조 일꾼(에이전트)에게 위임할까요?
코드 수정이니 무조건 Sonnet에게 위임한다
메인이 직접 한다 — 단일 파일 + 20줄 이하 단순 수정은 위임 면제
안전하게 3개 에이전트에 나눠 맡긴다
정답: 메인이 직접 — 위임은 한 번에 고정 비용(약 16K~25K 토큰)이 들어, 작은 일은 직접이 이득입니다. 판단 기준은 "코드냐"가 아니라 독립성·규모·맥락 격리로 2026-05-28에 재정의됐습니다. "코드 작업=무조건 Sonnet 위임"은 폐기된 옛 기준이에요.
PHASE 5 · MCP
🧪 시나리오 #10
새 PC로 복제했더니 6개 MCP가 모두 "Connected"인데, npx로 띄운 일부가 실행 단계에서 자꾸 실패합니다. 복제 때 얻은 핵심 교훈은?
MCP 서버를 모두 최신 버전으로 업데이트해야 한다
Windows에선 맨 npx 호출이 프로세스 스폰에 실패하므로, 연결을 cmd /c <직접 바이너리>로 통일해야 한다
방화벽에서 포트를 열어주면 해결된다
정답: cmd /c 직접 바이너리로 통일 — Windows에서 맨 npx 호출은 프로세스 스폰에 실패합니다. 그래서 6개 MCP 전부 cmd /c로 바이너리를 직접 호출하도록 통일한 게 새 PC 복제의 핵심 교훈이었습니다. (참고: notebooklm 미인증·Google Drive 스코프 부족은 별개의 "쓸 수 없음" 이슈)
PHASE 6 · 결함·설계 결정
🧪 시나리오 #11
새 PC에서 "MCP Connected · 훅 배치됨 · 설치 기록됨"으로 다 떴습니다. 이걸 보고 "정상 동작한다"고 보고해도 될까요?
된다 — Connected/배치됨이면 동작이 보장된다
안 된다 — "등록 ≠ 동작". 전수 검증으로 실제 실행을 확인해야 한다
일단 보고하고 문제가 생기면 그때 고친다
정답: "등록 ≠ 동작" — 복제 후 전수 검증에서 "Connected인데 실제론 안 도는" 결함이 6건 나왔습니다(린터 미설치·인증 2종·restore 훅 2종·날짜 UTC 어긋남). 가장 무서웠던 건 setup-new-pc.ps1이 BOM 없는 UTF-8이라 한글이 깨져 파싱에서 즉사한 것 — "파일은 있는데 안 돌던" 진짜 원인이었습니다. 그래서 완료 보고는 항상 end-to-end 실행 결과로 합니다.
PHASE 6 · 자기교정
🧪 시나리오 #12
사용자가 같은 실수를 두고 "또 안 지켰네"라며 세 번째로 지적했습니다. 봇은 어떻게 반응하도록 설계돼 있나요?
사과만 하고 같은 메모리에 다시 기록한다
피드백 카운터가 3회에 도달 → "정식 규칙(rules/)으로 승격할까요?"라고 제안한다
즉시 자동으로 규칙 파일을 만들어 강제 적용한다
정답: 3회 도달 → 규칙 승격 제안 — Reflexion 패턴입니다. 실수 횟수를 feedback-violations.json에 누적하다 3번에 닿으면 메모리 레이어(약함 30~50%)에서 규칙 레이어(매 세션 강제 70~80%)로 올릴지 제안합니다. 승인 없이 자동 승격하지는 않아요. P2.1의 "4단 설명·5줄 요약·즉시 전달"이 모두 이렇게 올라간 규칙입니다.
